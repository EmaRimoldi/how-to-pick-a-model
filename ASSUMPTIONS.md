# Assumptions

- `Document_2_Implementation_Guide.md` is the operational source of truth because local PDF text extraction is unavailable.
- The original `/Users/emanuelerimoldi/Documents/GitHub/stateful_query_engine` repository is read-only for this work session. Reused source is copied into the new repository.
- The new project directory is not a Git repository at the start of work, so the requested phase commits are skipped unless a `.git/` directory appears later.
- External model backends may be unavailable. The first complete experiment uses `local_stub`, a deterministic mock backend that satisfies the same six-mode protocol.
- Incorrect or invalid branches remain part of the branch tensor and estimator calculations. They receive the configured incorrect gain penalty for routing diagnostics.
- In the default C(a) `top1_only` regime, the selected top-probability branch is promoted even if it is incorrect, matching the protocol's online visibility rule.
- The first implementation prioritizes clean routing supervision data and smoke validation; LoRA/QLoRA training entrypoints are scaffolded but do not train unless explicitly run later.
- Routing gain targets are computed over the requested/declared branch mode so every step has exactly one candidate per mode. Inferred modes are also logged and used by mode-conditioned diagnostic summaries.
- New smoke/protocol runs use `hard_optimization` as the only active benchmark profile. Small `instance_overrides` may still be used for quick validator tests.
- Earlier Phase 2/3 historical artifacts used multiple profile names; those are preserved as historical data but no longer define the active benchmark.
- In C(a), previous `mode_probs` remain visible in history because they are part of the model's own prior decision state. Offline branch feedback for non-selected modes is the leakage-sensitive object and is excluded from next-step visible branch history.
- Phase 2 run directories remain under `runs/phase2_dev/`; repository `.gitignore` excludes `runs/*`, so committed Phase 2 outputs are the compact artifacts under `artifacts/` plus configs/tests/code.
- Phase 3 used Claude CLI transport because `ANTHROPIC_API_KEY` was not present. The backend also includes a direct Anthropic Messages API transport for environments with an API key.
- The configured `claude_haiku` model id is `haiku`, which the local Claude CLI mapped to a current Haiku model during live runs.
- Phase 3 uses reduced benchmark `instance_overrides` for the named profiles, matching Phase 2's protocol-validation style and keeping verifier runtime bounded.
- Claude CLI token counts include cache creation/read tokens from Claude Code's runtime context. They are useful for cost tracking but should not be interpreted as minimal prompt-token counts for a direct Messages API implementation.
- Claude candidate generation is protocol-configurable. `replacement_file` was frozen after Phase 3.5 because it beat `patch_unified_diff`, but that decision is now superseded for future runs by `structured_edits`, which avoids full-file outputs while also avoiding unified-diff hunk fragility.
- Deterministic local/mock backends may continue to write complete candidate files directly because they are protocol-test utilities, not cost-sensitive real-model editing backends.
- Future Phase 4 teacher runs should start with the `structured_edits` C(a) protocol, with `claude_opus_teacher_replacement_legacy` kept only as a fallback if structured edits prove unstable in a live smoke.
- Claude Opus teacher runs use the same Claude CLI transport as Haiku and the `claude_opus_teacher` model config. The local CLI maps `--model opus` to `claude-opus-4-6`.
- Opus production collection is treated as budget/availability constrained. Completed steps from an interrupted run are usable only when `vao.validate_run` passes on the run directory.
- The first Phase 4 teacher routing dataset combines validated pilot runs and the validated partial production run because the target production matrix was interrupted by `claude_cli_failed:1`.
- The first Phase 5 routing-only student used `sklearn` TF-IDF plus logistic regression before the local LoRA stack was installed. This remains a lightweight local routing student, not an end-to-end code-editing model.
- The Phase 5 online experiment isolates routing only by using the trained student for mode probabilities and deterministic local-stub candidate edits for all six branches.
- Claude quota is unavailable as of the offline pause milestone, so no new Claude, Opus, Haiku, Anthropic API, or Claude CLI experiments are run. Existing validated teacher data remains usable for offline analysis.
- Replay routing evaluation is one-step logged-counterfactual replay. It can compare decisions at checkpoints with already materialized six-branch tensors, but it cannot claim that alternate future checkpoints would match a true live run after a different branch is promoted.
- `peft` and `trl` were installed locally for routing-only experiments; `bitsandbytes` is intentionally skipped on this macOS arm64 environment because it is CUDA-oriented.
- A cached `distilbert-base-uncased` model is available locally and can be LoRA-tuned without downloads. Its current routing result is supplemental because it uses a tiny train/eval split rather than leave-one-out cross-validation.
- The current 12-example teacher routing dataset is treated as sufficient for plumbing, audits, and offline baselines, but insufficient for a positive routing-student scientific claim. Missing productive labels for `topk` and `summaries` make class-balanced training impossible until more teacher data is collected.
- Historical token/cost accounting for Claude replacement runs includes the full distribution prompt, six candidate-generation calls, full replacement-file outputs, Claude CLI cache creation/read tokens, and repair calls when present. It should not be interpreted as the cost of editing only one or two lines.
- The new `structured_edits` protocol is the intended route for line/function-local edits. In production/prompt-controlled mode it should be run as batched generation: one model prompt returns `mode_probs`, `mode_ranking`, and all six compact edit operations, then the framework applies each edit to its isolated branch copy.
- C(b) feedback-use diagnostics are now implemented as an optional protocol condition. The local validation uses deterministic backends only; a real C(b) measurement of feedback use requires a live model call for `q_post` after showing all six branch results.
- Controlled mode selection is an experimental override. When `selection_policy` is not `top1`, `selected_mode_top1` still records the model argmax, while `selected_mode` records the branch actually promoted as parent.
- A one-step Haiku smoke shows the fastest current real-model route is batched `structured_edits`: one Claude call returns `mode_probs` plus all six branch-local edit candidates. This reduces repeated context/token overhead compared with six serial candidate calls.
- The batched `structured_edits` result is a speed/cost finding, not yet a production-quality teacher-data decision. One of six batched candidates was rejected by source safety validation and logged as a no-op, so prompt/repair hardening is required before scaling.
- New benchmark runs now use a single canonical profile, `hard_optimization`. Older profile names may remain in historical run artifacts, docs, and offline datasets, but the active benchmark configuration and experiment configs should not use them for new runs.
- `hard_optimization` is intentionally mixed rather than mode-specific: all nine workload families are included so that routing has to manage tradeoffs among indexing, summaries, top-k, caching, layout, and micro edits.
- On `hard_optimization`, local calibration suggests a baseline verifier cost of about 65 seconds and a post-baseline six-branch step cost of about 78 seconds for deterministic local candidates.
- The validated Haiku batch hard smoke took 346.4 seconds total for one step including baseline, cost `$0.171`, and had zero proposal/source/verifier failures. A 3-step Haiku pilot is estimated at about 15 minutes serial wall-clock and roughly `$0.51`, subject to candidate runtime variance.
- The first validated 3-step Haiku batch pilot took 807.0 seconds total and cost `$0.600`. The prompt still needs hardening against banned `list.remove` calls, which caused two candidate rejections.
- Deterministic source repair is allowed only for narrow, auditable safety-screen overreach. The current repair rewrites simple `.remove(...)` calls when that is the only validation error and logs the repair; it does not repair semantic algorithm errors.
- `top_k` semantic errors are not locally rewritten. They remain verifier-evaluated candidate failures, while prompts specify the required `(-value, key)` ordering more explicitly.
- The first open-weight "weak/stupid" model is `Qwen/Qwen2.5-Coder-1.5B-Instruct`, selected because it is small, ungated, code-oriented, and runnable on a single Engaging L40S GPU without new vendor quota.
- `weak_qwen` uses an OpenAI-compatible chat endpoint. For the first smoke, Qwen was served with the minimal local `transformers` server in `scripts/qwen_openai_compat_server.py`; this is a smoke/debug server, not a production-throughput replacement for vLLM or SGLang.
- Qwen 1.5B has historically not reliably satisfied the full all-in-one batch JSON contract. The legacy `weak_qwen` adapter may fall back to per-mode structured-edit calls for debugging, but prompt-controlled comparisons must use `weak_qwen_batch_strict`, which disables per-mode fallback and batch repair.
- Deterministic JSON repairs for open-weight models are allowed only before normal validation. Current repairs handle fenced JSON, triple-quoted Python string values, and unindented `replace_function` method bodies; repaired candidate sources still pass the same parser, source validator, and verifier path before they can be evaluated.
- The `weak_qwen_direct` backend gives the model direct branch-local file editing through LangGraph, but not unrestricted terminal access. Tools are limited to `read_file`, exact replacements/insertions/deletions, `replace_function`, validation, and finish, all bound to a single branch's `proposed_solution.py`.
- Direct-file editing is per-mode only for now. It preserves six isolated C(a) branches by running one LangGraph editor loop per mode branch after the shared mode distribution is sampled.
- The first Haiku-vs-Qwen hard-profile comparison is a system/backend comparison, not a pure model-only comparison. Haiku used batched structured edits in one Claude call per step; Qwen used one mode-distribution call plus six LangGraph direct-file-edit loops against an OpenAI-compatible local endpoint.
- Qwen local serving reports no USD cost because it uses the Engaging GPU allocation rather than a metered vendor API. Wall-clock and token counts are still logged and comparable as engineering metrics.
- The initial 10-step comparison is an R0 calibration run. Its routing and loss trends are useful for debugging and experiment sizing, but at least a few repeats are needed before claiming stable Haiku-vs-Qwen performance differences.
- The R0-R2 Haiku-vs-Qwen summary reports routing correctness against the declared branch mode with minimum verified `latent_loss`. This is distinct from `inferred_mode`, which is the diff classifier output and may classify many small direct-file edits as `micro` even when the controlled branch was requested as another mode.
- The R0-R4 Haiku-vs-Qwen aggregate includes only complete validated 10-step runs. Partial Haiku trials `hard_haiku_batch_10step_r3`, `hard_haiku_batch_10step_r3_retry1`, and `hard_haiku_batch_10step_r4` are treated as failed trials and excluded from primary aggregate metrics.
- In R0-R4 summaries, `best_visible_loss` is the minimum verified loss among promoted branches only, while `best_counterfactual_loss` is the minimum verified loss among all offline branch evaluations. `branch_correctness_rate` means verifier semantic correctness, not optimization success.
- Candidate preflight is treated as part of the verifier front-end. If a generated branch fails deterministic constructor/API/top_k/aggregate_count checks, it receives a logged verifier outcome with `correctness=false` and `latent_loss=inf` without running the full benchmark. This preserves the six-branch C(a) tensor while avoiding expensive evaluation of obviously invalid code.
- Prompt hardening is allowed to constrain invalid edits and degenerate routing, but the framework still records the model's explicit normalized `mode_probs`; it does not forcibly rebalance Qwen probabilities in code.
- Preflight is not a model prompt. It is a local verifier-side semantic smoke test applied equally to Haiku, Qwen, local, and future backends before expensive benchmarking.
- Prompt-controlled comparisons require one model-generation prompt per step. All real-model prompt paths include the same `CANONICAL_TASK_BLOCK_V1`; the paired Haiku/Qwen prompt-controlled configs use the same batched structured-edit output contract and disable per-mode fallback.
- The R0-R4 Haiku batch vs Qwen direct aggregate remains a system/backend comparison because Haiku used one batched structured-edit call per step while Qwen used a distribution call plus six direct-file tool loops. A pure prompt-controlled comparison should use the paired single-prompt batched configs for both Haiku and Qwen.
- `weak_qwen_local_cached_batch_strict` is a local infrastructure smoke alias for cached `Qwen/Qwen3-0.6B-Base`, not the primary Qwen Coder baseline. Its batch output is capped lower than GPU Qwen because local MPS generation is much slower.
- `Qwen/Qwen2.5-Coder-1.5B-Instruct` can run locally on MPS through the smoke OpenAI-compatible server. Throughput should not be interpreted as Engaging GPU throughput, but protocol validity is meaningful because the same strict single-prompt adapter path is used.
