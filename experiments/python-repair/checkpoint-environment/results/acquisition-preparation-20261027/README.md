# Public acquisition snapshots and development preparation

A durable acquisition now preserves **the trace actually observed**, bound to
its public code/input/feedback and runtime source hashes. Loading and projecting
it never reruns the candidate. Eight development tasks have available snapshots
and sixteen matched inert prompts. **No new model request has been sent and no
repair-benefit claim follows.**

## Why the next comparison changes its development bank

A separate offline audit retained all twelve original model-generated
checkpoints and compared old/new traces on all eight public failures. **Seven
have exactly the same event values**, after removing the new sequence and
function-definition metadata. Only httpie/5 changes retained observations,
adding constructor-region coverage. Metadata changes are not new runtime facts.
This does not prove that traces can never help those bugs, but it gives little
reason to rerun the old cohort as a test of the retention revision.

The full original-checkpoint report, original audit source and hashes are saved
alongside the preparation. Original source IDs, public outcomes, non-triggering
candidates and all records remain preserved. No model outcomes were sampled to
choose these findings, and no historical gate or score was altered.

## New prepared bank

The six [broader adapters](../../development-broader/README.md) plus two
[stateful/recursive adapters](../../development-stateful/README.md) give eight
original buggy artifacts, all failing public tests. A first failing public case
is selected by its existing order; no evaluator, reference or fault-location
criterion selects a diagnostic. Shared public verification and an additional
ordinary/traced pair are recorded per task. All eight pairs agree with their
public feedback and their diagnostics are available.

These checkpoints are **original programs after failed public tests**, not
model-generated failed repairs. Six sources have already been used in the
closed one-draw initial calibration. The two new adapters were already exposed
at source-screening level. Everything is development data. A model study here
could test information value in another repair setting, but cannot establish
conditional recovery of generated failed patches, generalization or the final
policy objective. The earlier six-task recovery stage stays closed.

Each matched pair has identical system instructions, code, tests, expected
values and public observations. Only `runtime_diagnostic` differs. Both requests
remain `provider_call_enabled: false`, without provider bodies or live admission.
The largest message-byte-plus-4096-framing allowance is **30,623**; this is a
conservative reservation input, not a tokenizer measurement.

## Acquisition semantics

`vao.repair.acquisition_snapshot` claims a fresh directory before execution,
then stores the diagnostic and seals its exact identity. A second acquisition
at that path fails before execution. An interruption leaves an uncompleted claim;
it cannot be loaded or resumed. Unavailable or observation-mismatched diagnostics
are completed records with explicit missing information, never silently dropped.
No-public-failure records make zero acquisition calls.

A loader verifies the public checkpoint, runtime identities when supplied by a
freeze, actual stored trace bounds, availability and resource counts, plus the
claim/snapshot/completion hashes. Prompt projection loads that sealed record
itself. Altered code, feedback, trace bytes, counts, frozen runtime or seal are
rejected. Hashes bind recorded data; they do not certify the truth of arbitrary
candidate-generated values. Ordinary/evaluator execution remains the only
correctness judge.

Stored trace hashes/set-order values are not normalized or replaced. Replicating
model generations against one snapshot conditions on that acquired trace;
it does not estimate variability across independent trace acquisitions. A later
protocol must explicitly choose how such acquisitions are replicated and
charged. The existing code limits/object omissions of the balanced tracer still
apply.

Shared test execution, extra diagnostic executions, acquisition seconds and
preparation time including I/O/projection are saved. Preparation excludes pool
loading and preflight; these are not comprehensive deployment-cost results.
A real never-diagnose policy would not pay for diagnostic acquisition, whereas
paired experimental preparation computes the treatment offline. Cached diagnostic
work must still be charged per counterfactual deployment in a later policy study.

## Planning arithmetic, not collection authorization

A possible two-arm, two-draw study over eight tasks would make 32 requests.
With a 40,960 input-token reservation ceiling, 8,192 maximum output tokens and
price ceilings 0.12/0.80 USD per million, the maximum reservation is
**$0.0114688 per call; $0.3670016 total**. Adding the existing $0.20937371 once
would give $0.57637531, below the retained $0.60 ceiling. These are conservative
planning bounds, not live prices, actual spending or a new allocation.

An 8,192-token output allowance avoids declaring a full-file repair experiment
with the previous smaller bound without first considering the longer source.
It is shared by both proposed arms; output adequacy is not guaranteed. Model,
provider availability/prices, protocol, cell schedule, accounting, analysis,
collector integration, source freeze and exact-head CI must be reviewed before
any request. This bundle does not start, register or authorize a study.

## Reproduction

The inert archive contains all eight public workspaces/observations, actual
acquisition claims/snapshots/seals, sixteen prompts, accounting, pool definitions
and eight runtime source files as text. Its SHA-256 is
`353394a00c57f206c7f29d647ba722cc3731f1c61083bb39672f814c674f00e3`.
[reverification.json](reverification.json) records successful reconstruction of
all prompt cores, snapshot identities, input-source mappings and resource counts.

Read-only audit from the repository root, with no candidate execution:

```bash
uv run python experiments/python-repair/checkpoint-environment/results/acquisition-preparation-20261027/reproduce.py
```

Fresh acquisition requires the native sandbox and a new output path:

```bash
uv run python scripts/prepare_repair_acquisition_snapshots.py \
  --pool experiments/python-repair/checkpoint-environment/development-broader \
  --pool experiments/python-repair/checkpoint-environment/development-stateful \
  --output runs/public-acquisition-fresh
```

A fresh run can legitimately contain different intermediate stochastic values
and timings. It is a different acquisition, never a replacement for the saved
one. No old provider request is retried or reopened by either command.
