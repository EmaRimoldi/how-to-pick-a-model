You are running one step of an autonomous code-optimization experiment.

The task is to improve a single Python file, solution.py. During evaluation,
the framework will place your file next to a fixed read-only prepare.py and run
it as train.py on a CPU-only CIFAR-10 benchmark. You are not running the
evaluator yourself. The framework will materialize your proposed edits,
evaluate them offline, and promote only one branch according to your own mode
probability distribution.

Experiment setup:

- The current parent solution.py below is the only online code state visible to
  you for this step.
- The visible history contains only information that the online agent is
  allowed to know under the current visibility regime.
- The framework copies the exact same parent solution.py into six isolated
  branch directories, one branch per primary mode.
- You must propose exactly one candidate edit for each primary mode in a single
  JSON response.
- The evaluator will run your candidate with fixed-step training on CPU and
  record validation loss (`val_loss`, lower is better). A branch that crashes,
  violates the contract, or returns NaN is a failed branch.

Goal:

Minimize verified validation loss while preserving executability and contract
compliance. A branch that trains stably and improves loss is better than a
clever branch that crashes.

Primary modes:

- layout: architecture and model-capacity changes such as depth, width,
  classifier shape, or normalization layout.
- indexing: optimizer-family and gradient-dynamics changes such as Adam/AdamW/SGD,
  momentum, betas, or related optimizer helpers.
- topk: learning-rate scale changes. Treat this as the branch for adjusting
  step size or nearby scalar optimization magnitudes.
- caching: regularization and robustness changes such as weight decay, dropout,
  or other anti-overfitting edits.
- summaries: schedule and budget-allocation changes such as warmup, cosine
  decay, decay milestones, or how the fixed training budget is used.
- micro: batching, loop-local stability, or small training-script cleanups.

These six names are canonical experiment labels. They are not literal code
permissions. Use them to indicate the dominant training idea of the candidate.

Required contract after every branch edit:

- The file must remain a valid Python training script.
- It must define the existing constants and entrypoints used by the baseline:
  `SEED`, `DEPTH`, `BASE_CHANNELS`, `CHANNEL_MULT`, `USE_BATCHNORM`,

- Do not use file IO, network, subprocess, eval, exec, or hidden global state.
