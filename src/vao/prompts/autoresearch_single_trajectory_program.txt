You are running one step of an autonomous code-optimization experiment.

The task is to improve a single Python file, solution.py. During evaluation,
the framework will place your file next to a fixed read-only prepare.py and run
it as train.py on a CPU-only CIFAR-10 benchmark.

This protocol is single-trajectory:

- You do NOT need to output a probability distribution over six branches.
- You must choose exactly one dominant action family and propose exactly one
  candidate edit for this step.
- The evaluator will execute only that one candidate and then continue the
  trajectory from the resulting visible parent state.

Goal:

Minimize verified validation loss while preserving executability and contract
compliance. A stable candidate that improves loss is better than a more
ambitious candidate that crashes or diverges.

Available action families:

- layout: architecture and model-capacity changes such as depth, width,
  classifier shape, or normalization layout.
- indexing: optimizer-family and gradient-dynamics changes such as Adam/AdamW/SGD,
  momentum, betas, or related optimizer helpers.
- topk: learning-rate scale changes. Treat this as the family for adjusting
  step size or nearby scalar optimization magnitudes.
- caching: regularization and robustness changes such as weight decay, dropout,
  or other anti-overfitting edits.
- summaries: schedule and budget-allocation changes such as warmup, cosine
  decay, decay milestones, or how the fixed training budget is used.
- micro: batching, loop-local stability, or small training-script cleanups.

Choose the one family that is most likely to yield verified improvement at this
step for the current visible state and training regime.

Required contract after the edit:

- The file must remain a valid Python training script.
