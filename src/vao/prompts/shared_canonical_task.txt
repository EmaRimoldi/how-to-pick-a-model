CANONICAL_TASK_BLOCK_V1

You are participating in a verifiable agentic optimization experiment.

Canonical task:

- Edit one visible parent solution.py implementing CandidateQueryEngine.
- The framework copies the exact same parent into six isolated branch directories,
  one per primary mode.
- Each branch candidate must start from that parent only. Do not assume, observe,
  or reuse edits/results from any other branch in the same step.
- The verifier evaluates all six branches offline. Only the top-probability mode
  under the model's mode_probs is visible/promoted to the next online state.
- Do not use offline counterfactual branch results unless they appear in
  visible_history.

Canonical modes:

- layout: changes primary storage representation, __init__, put, delete, or get.
- indexing: changes range-query access paths, sorted keys, bisect, range bounds, or range slicing.
- topk: changes top_k, heapq use, sorting, or tie-breaking.
- caching: adds or changes memoized query results and invalidation.
- summaries: adds or changes maintained aggregates such as prefix sums, Fenwick trees, buckets, or aggregate arrays.
- micro: local constant-factor edits without a structural algorithm change.

Required API after every branch edit:

- Define class CandidateQueryEngine.
- Implement put(key:int, value:int)->None.
- Implement delete(key:int)->None.
- Implement get(key:int)->int|None.
- Implement range_sum(lo:int, hi:int)->int.
- Implement aggregate_count(lo:int, hi:int)->int.
- Implement top_k(lo:int, hi:int, k:int)->list[tuple[int,int]].
- Range bounds are inclusive: lo <= key <= hi. Empty ranges return 0 or [] as appropriate.
- aggregate_count must count keys satisfying inclusive bounds lo <= key <= hi; it must not sum values.
- top_k must sort by value descending, then key ascending.
- top_k tie-breaking is strict: if two rows have the same value, the smaller key must appear first.
- If using sorting, use exactly the semantic key lambda item: (-item[1], item[0]).
- If using heapq, push/compare tuples equivalent to (-value, key) so ties prefer smaller keys.

Representation consistency:

- If you introduce or rename storage fields such as _items, _keys, _values,
  _sums, caches, buckets, or trees, update __init__ and every method that reads
  or writes that representation in the same candidate.
- Do not mix incompatible representations. A candidate that adds _items while
  any method still reads _keys/_values, or vice versa, is invalid.
- Layout edits must preserve get/range_sum/aggregate_count/top_k semantics.
- Non-layout modes should avoid changing primary storage representation.

Safety constraints:

- The materialized code after each branch edit must be self-contained.
- Allowed imports: __future__, array, bisect, collections, dataclasses, heapq, itertools, math, typing.
- No file IO, network, subprocess, eval, exec, dynamic imports, or hidden global state outside each instance.
- Do not call banned attributes: connect, mkdir, open, popen, read_bytes, read_text, remove, rename, replace, rmdir, socket, system, unlink, write_bytes, write_text.
- For list deletion, use comprehensions, slices, pop(index), or rebuilt lists; do not use list.remove.
- For sorted-key deletion, prefer `idx = bisect.bisect_left(keys, key)` followed by an equality check and `keys.pop(idx)`. Never use `keys.remove(key)`.
- Do not import the benchmark, reference implementation, or previous candidates.
- Do not include chain-of-thought.
- Keep each candidate scoped to its requested primary mode.

Mode probability requirements when the prompt asks for routing:

- mode_probs must contain exactly layout, indexing, topk, caching, summaries, micro.
- Probabilities must be numeric and nonnegative.
- The framework normalizes probabilities if they are slightly off, but you should sum to 1.
- mode_ranking must be a permutation of the six modes sorted from most to least promising.
- Do not use `layout` as a default high-probability mode. Assign probability by expected marginal verified gain for the current parent and profile.
- If recent visible history shows a selected mode produced poor gain or incorrectness, lower that mode unless the current parent clearly changed the opportunity.
- Keep enough probability mass on non-layout modes when the profile stresses range queries, top_k, repeated windows, or aggregate counts.
- If layout was selected in recent visible history and produced only small gain, make a non-layout mode top-ranked unless there is specific evidence that the parent representation is now broken.
- Avoid assigning more than 0.40 probability to any one mode unless the current parent/source gives a clear concrete reason.
