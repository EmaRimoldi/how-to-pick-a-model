This is an experiment in autonomous research on a verifiable training task.

You are running one step of an AutoResearch-style code-optimization loop. The
task is to improve a single Python file, solution.py. During evaluation, the
framework will place your file next to a fixed read-only prepare.py and run it
as train.py on a CPU-only image-classification workload.

The original AutoResearch loop lets an agent edit train.py, run uv run train.py,
commit promising changes, discard failed changes, and continue indefinitely. In
this benchmark, the framework implements that loop for you:

- You do not create branches, commits, logs, or results.tsv.
- You do not run the verifier yourself.
- You propose compact structured edits to solution.py.
- The framework materializes the edit as train.py, runs the verifier offline,
  promotes successful changes according to the experiment policy, and records
  the result.

Setup:

- prepare.py is fixed and read-only. It defines the data pipeline, evaluator,
  and verifier contract.
- solution.py is the only file you may edit. It becomes train.py during
  evaluation.
- The current parent solution.py below is the only code state visible to you.
- The visible history contains only information available under the current
  visibility regime.
- Profile summary describes the workload instance: model family, dataset
  regime, subset sizes, label noise, imbalance, seed, and training budget.

Goal:

Minimize the verified validation loss while preserving executability and
contract compliance. This is the same role played by val_bpb in the original
AutoResearch language-model setting, but the active CIFAR-10 verifier reports
val_loss and val_accuracy. Lower val_loss is better. A stable, simple change
that improves loss is better than an ambitious change that crashes, diverges, or
adds unjustified complexity.

What you can do:

- Modify model architecture, optimizer, hyperparameters, scheduler, batch size,
  training loop details, and other code inside solution.py.
- Use the current source, profile summary, and visible history to choose the
  next experiment.
- Prefer simple changes when expected gains are comparable.
- Keep simplifications that preserve or improve verified loss.

What you cannot do:

- Do not modify prepare.py or the evaluation harness.
- Do not install packages or add dependencies.
- Do not use file IO, network, subprocess, eval, exec, or hidden global state.
- Do not assume access to offline branch results unless they appear in visible
  history.
- Do not output a full replacement file.
- Do not include chain-of-thought.

Required contract after every edit:

- The file must remain a valid Python training script.
- It must define the existing constants and entrypoints used by the baseline:
  `SEED`, `DEPTH`, `BASE_CHANNELS`, `CHANNEL_MULT`, `USE_BATCHNORM`,
  `DROPOUT_RATE`, `FC_HIDDEN`, `OPTIMIZER`, `LEARNING_RATE`, `WEIGHT_DECAY`,
  `MOMENTUM`, `ADAM_BETAS`, `USE_LR_SCHEDULE`, `BATCH_SIZE`, `NUM_WORKERS`,
  `CIFAR10Net`, `build_optimizer`, `build_scheduler`, and `main`.
- It may import only standard baseline dependencies already present in the
  parent file.

Action-family labels:

The framework uses six canonical labels to describe the dominant idea of an
edit. These labels are for logging, routing, and counterfactual analysis; they
are not literal permissions and they are not a whitelist of lines to modify.

- layout: architecture and model-capacity changes such as depth, width,
  classifier shape, normalization layout, or residual structure.
- indexing: optimizer-family and gradient-dynamics changes such as Adam,
  AdamW, SGD, momentum, betas, clipping, or related optimizer helpers.
- topk: learning-rate scale changes and nearby scalar optimization magnitudes.
- caching: regularization and robustness changes such as weight decay, dropout,
  augmentation robustness, or anti-overfitting edits.
- summaries: scheduler and budget-allocation changes such as warmup, cosine
  decay, milestones, or use of the fixed training budget.
- micro: batching, loop-local stability, numerical hygiene, or small
  training-script cleanups.

Choose the action family that best describes the main experimental idea. If the
required JSON schema asks for six candidates, produce one coherent candidate for
each family and assign probabilities by expected marginal verified gain. If the
schema asks for one candidate, choose the single most promising family and
produce one candidate. In all cases, follow the Required JSON schema appended
after this prompt exactly.

Structured edit rules:

- Use 1 to 8 edits. Prefer the fewest edits that are sufficient.
- Use one of these operations:
  - replace_exact: {"op":"replace_exact","old":"exact existing text","new":"replacement text"}
  - delete_exact: {"op":"delete_exact","text":"exact existing text"}
  - insert_before: {"op":"insert_before","anchor":"exact existing text","text":"inserted text"}
  - insert_after: {"op":"insert_after","anchor":"exact existing text","text":"inserted text"}

- Exact text and anchors must occur exactly once in the parent file.
- replace_function is preferred when changing a whole helper or main; exact
  edits are preferred for constants and small local changes.
