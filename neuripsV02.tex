\title{How to Pick the Model:\
Minimal Diagnostic Interaction for Verifier-Backed Agentic Systems}

\author{Anonymous Authors}

\begin{document}

\maketitle

\begin{abstract}
Verifier-backed agent systems are often evaluated by whether a model can eventually solve a task.
For deployment, the sharper question is temporal and decision-theoretic: given a verifier-backed task family, a finite menu of model or harness actions, and a cheap information channel before the costly deployment attempt, which action should the system choose to reach a verified success fastest, cheapest, and robustly on the current instance?
Following the time-centric view of verifiable transduction in Achille--Soatto, we treat useful task information as information that reduces search time to a verified solution rather than as an intrinsic model score.
Many such tasks admit a small diagnostic interaction with the task and verifier before the deployment action is chosen.
We formalize the router--verifier interaction as a \emph{diagnostic interface}: a standardized cheap protocol in which the verifier acts as the measuring instrument that converts limited task contact into a router-visible signal $Z_b$.
The router may itself be an LLM orchestrator that controls a menu of candidate workers, and the chosen worker carries out the costly deployment attempt from the declared initial state.
For any deployment loss, especially the cost-aware persistence losses used below, we give an exact accounting identity that can diagnose how much value is available from static context, diagnostic interaction, and router use of the resulting signal.
We then define the minimum useful diagnostic interaction as the cheapest admissible measurement that recovers a target fraction of the routing value, or equivalently yields positive value after its own cost is charged.
The experimental program instantiates the formalism on AutoResearch-style CIFAR-10 optimization with prompt-only Opus routing over a Haiku/Sonnet/Opus worker menu.
AutoResearch is used as a controlled member of a broader class of verifier-backed tasks: agents edit an executable artifact, receive external validation feedback, and are evaluated by verified improvement, persistence, and resource cost under a fixed budget.
The main diagnostic family includes no interaction, read-only task views, and one or two cheap verifier-only baseline probes before routing.
The paper contributes a deployment-facing theory of minimal verifier-backed measurement and a benchmark protocol for testing whether diagnostic information changes LLM router allocations and lowers selected-worker deployment loss.
\end{abstract}

\section{Introduction}
\label{sec:intro}

Modern agentic systems are increasingly deployed on tasks whose success is externally checkable: a patch passes tests, a proof checks, a data pipeline satisfies validation constraints, or a training program improves held-out performance.
In these settings, the practitioner rarely faces a single-model question.
They face a portfolio decision under time and cost pressure.
A stronger model may be more competent but slower and more expensive; a smaller model may be cheaper but unreliable; a harness may trade additional retries or tool calls for better success probability.
The operational question is therefore not which model has the highest aggregate benchmark score, but which deployable action should be launched on this particular instance, under this verifier and budget.

This view aligns with the time-centric formulation of agents in \citet{achille2025agents}: for verifiable transductive tasks, eventual solvability is too weak a notion of capability.
What matters is the path to a verifier-accepted output and the resources spent along that path.
A model that eventually succeeds after a long search can be inferior, in deployment, to a cheaper model that reaches a slightly weaker but sufficient certified outcome quickly and reliably.
Conversely, a model with the best final validation score may be the wrong choice if its cost or latency dominates the value of that improvement.

The verifier changes the nature of the routing problem.
It is not only the final judge of success; it can also be used as a measuring instrument before the costly deployment attempt.
Before committing to a full run, a system may inspect the artifact, run a smoke test, call a checker on a bounded attempt, or evaluate an unmodified training program under a small validation budget.
Such interactions are not generic prompt features.
They are task-specific measurements produced by the same external mechanism that will later certify success.
When they reveal which available action has a short path to success, they can change the economically correct model choice; when they are uninformative or too expensive, the best static choice should remain unchanged.

This paper studies that pre-deployment measurement problem for verifier-backed LLM agents.
We separate three roles that are often conflated.
The verifier evaluates candidate artifacts.
The worker is the solver policy that acts on the task instance.
The router is a meta-level LLM orchestrator that observes a pre-decision information state and chooses the worker or harness action to deploy.
The diagnostic signal does not make any worker intrinsically stronger.
It can only help by changing the router's allocation toward an action with lower verifier-indexed deployment loss.

We ask whether model or harness choice for verifier-backed agents can be turned from benchmark racing into controlled router decisions under a predeclared deployment loss.
Given a finite worker/action menu, we compare the same LLM router under static context alone and under additional verifier-derived diagnostic records.
The main empirical quantities are the router's allocation shift, the paired change in selected-worker deployment loss, and the diagnostic cost paid to obtain the signal.
Oracle decompositions are useful for interpreting headroom, but the central claim is tested by relative router runs: does the diagnostic record change the actual router's choice, and does that change improve cost-aware verified performance?

We instantiate these claims on AutoResearch-style CIFAR-10 optimization, where an agent edits an executable training program and an external verifier returns validation metrics.
This task is a controlled substrate for the broader phenomenon: the artifact is concrete, the verifier is cheap enough to query before deployment, and counterfactual worker trajectories can be collected on the same instances.
The benchmark uses compact convolutional networks, flat multilayer perceptrons, and tiny residual networks with repeated seeds, allowing us to measure whether verifier-backed diagnostic information adds value beyond static family identity.

This positioning leaves a concrete gap between algorithm selection, LLM routing, and verifier-backed agent evaluation: the field lacks an accounting language for deciding when a cheap verifier-derived signal is valuable enough to change the worker or harness action selected for deployment.
The paper makes four contributions.
\begin{enumerate}[leftmargin=1.35em,itemsep=0.2em]
  \item \textbf{Deployment-loss formulation.} We formulate finite-action model/harness selection under verifier-backed deployment losses, including first-hit, occupancy, and cost-aware variants.
  \item \textbf{Router--verifier diagnostic interface.} We define the verifier-mediated interaction that lets a router obtain a bounded, measurable signal about the current task before selecting the deployment action.
  \item \textbf{Diagnostic value accounting.} We give an exact identity that separates best fixed performance, static-context value, diagnostic signal value, measurement cost, and learned-router gap for interpreting headroom and failure modes.
  \item \textbf{Experimental program.} We specify an AutoResearch campaign that tests metric choice, diagnostic allocation shift, paired selected-worker deployment loss, and minimum useful interaction budget, with reusable-evaluation and oracle analyses moved to supporting diagnostics.
\end{enumerate}

\section{Related work and positioning}
\label{sec:related}

The closest classical ancestor is algorithm selection.
Since Rice's formulation, solver portfolios have treated performance as instance-dependent: SATzilla and AutoFolio, for example, learn to select solvers from instance features rather than report a single globally best solver~\citep{rice1976algorithm, xu2012satzilla, lindauer2015autofolio, kotthoff2016algorithm}.
That literature supplies the right high-level question, but its features are usually static descriptors computed before solving.
Our setting adds an active verifier-backed step: before selecting the deployment solver, the system may spend a small admissible budget to query the task and verifier, then decide whether that interaction changes the best action.

A newer line of work studies LLM routing and cascades.
FrugalGPT frames model cascades as a way to reduce cost across heterogeneous LLM APIs, while RouteLLM learns cost-quality routers from preference data~\citep{chen2023frugalgpt, ong2024routellm}.
Recent compound-system routing work extends the same idea to module allocation and multi-agent structures~\citep{chen2025optimizing, yue2025masrouter}.
These methods establish that heterogeneous model menus create economic gains, but they mostly operate on prompt-response workloads where routing signals are query features or learned response-quality predictors.
They do not ask how much task-specific verifier interaction is enough before committing to an expensive agentic deployment.

Verifier-backed agent benchmarks provide the task substrate.
SWE-bench evaluates repository repair against tests, AutoResearch evaluates training-loop edits against validation feedback, and theorem proving or configuration tasks use checkers and validators in analogous ways~\citep{jimenez2024swebench, karpathy2026autoresearch}.
Test-time compute work asks how far a solver can be pushed with more inference, sampling, or search~\citep{snell2025testtime, brown2024monkeys, wu2025inference}.
Our question is complementary: before spending that compute, should the deployment system change which model or harness action is selected, given a cheap verifier-derived signal?

This leaves a gap between algorithm selection, LLM routing, and verifier-backed agent evaluation.
What is missing is an accounting language that separates static context, verifier-derived diagnostic records, measurement cost, and router decision quality.
The contributions above target this gap: the router--verifier diagnostic interface defines the admissible measurement, the action menu and verifier-indexed loss measure its deployment value, and reusable evaluation records turn the idea into an experimental design.


\section{Verifier-backed Model Choice}
\label{sec:setup}

We formalize model choice as a verifier-backed deployment problem.
The system has a concrete task instance, a finite menu of deployable actions, and a fixed budget.
The question is which action should be launched after observing only the permitted pre-deployment information.

\subsection{Tasks, workers, and deployment loss}

\begin{definition}[Verifier-backed transductive deployment task]
A verifier-backed transductive deployment task is a tuple
$\cT=(\cX,\cY,V,B,\mu)$,
where $\cX$ is an instance space, $\cY$ is a space of candidate artifacts or solutions, $V$ is an external verifier or verifier-derived scoring procedure on instance--artifact pairs, $B$ is a deployment budget, and $\mu$ is a deployment distribution over instances.
The task is transductive because performance is measured on concrete pairs $(x,y)$, and verifier-backed because success and progress are determined by $V$ rather than by a model's self-report.
\end{definition}

The verifier may be binary, as in tests or proof checking, or scalar, as in validation loss, reward, energy, or score.
The essential requirement is externality: deployment performance is a function of what the verifier certifies and of the resources spent to obtain that certification.

\begin{definition}[Workers, deployable actions, and router]
Let $\cM=\{m_1,\ldots,m_K\}$ be a finite menu of candidate workers, i.e. models or fixed model harnesses that can attempt the task instance.
A worker acts on the task state and produces an artifact or solution; the object being optimized, repaired, proved, or configured is part of the task state, not the worker itself.
Let $\cA$ be a finite menu of deployable actions.
In the simplest worker-selection setting, $\cA=\cM$; more generally, an action $a\in\cA$ is a predeclared deployment policy, such as a worker together with fixed stopping, retry, or tool-use rules.
Each action incurs an integrable verifier-indexed deployment loss $\ell_V(a,X)$ derived from verified outcome and resource cost.
A router $R$ observes permitted pre-deployment information and selects an action from $\cA$.
\end{definition}

For readability we write $\ell(a,X)$ below, but the loss, observation distribution, and measurement cost are always indexed by the verifier, budget, and admissible protocol.
The conditional Bayes action under information $I$ is
\[
\argmin_{a\in\cA}\E[\ell(a,X)\mid I].
\]
A learned router is useful only insofar as its selected action approaches this loss-minimizing decision under the information it is allowed to see.

\subsection{Diagnostic measurements before deployment}

\begin{definition}[Observed context and diagnostic measurement]
Let $W=\omega(X)\in\cW$ be the coarse context observed before choosing the deployment action, such as problem family, repository type, theorem domain, artifact class, or benchmark split.
Let $\cB$ be a finite family of admissible diagnostic measurements.
Each $b\in\cB$ is a budgeted procedure, executed before the deployment action is chosen, that may inspect the instance and query the verifier only through predeclared channels.
Running $b$ on instance $X$ against verifier $V$ produces a diagnostic record $O_b^V(X)$, a router-visible signal $Z_b=\phi_b(O_b^V(X))$, and a diagnostic cost $c_b^V(X)$.
Admissibility means that the measurement action set, budget, stopping rule, recorded fields, and carryover rule are fixed before evaluation.
If a measurement modifies mutable task state, the modified state is discarded before deployment unless the carryover is explicitly included in the deployable action being evaluated.
\end{definition}

The diagnostic signal is not a capability increase for any worker.
It is a finite-budget measurement channel between the current task, verifier, and action menu.
It is decision-relevant when it changes the action that should be selected under the deployment loss, and useful only when the resulting loss reduction exceeds the measurement cost.
One information-only diagnostic is
\[
\MI(A^\star_\ell;Z_b\mid W)>0,
\qquad
A^\star_\ell(X)\in\argmin_{a\in\cA}\E[\ell(a,X)\mid X],
\]
but this is secondary to deployment value: a signal can reduce uncertainty about the best action and still be too expensive to use.

\subsection{Finite-budget deployment losses}

Achille--Soatto's proper-time view says that, in a verifiable task, a solver should be judged by the resource needed to reach a verifier-accepted output rather than by eventual solvability alone.
Our finite-deployment analogue fixes a horizon $H$ and a task-normalized verified progress process $G_t(a,x)\in[0,1]$, where larger is better and $t$ indexes a predeclared resource unit such as verifier calls, wall-clock time, or model steps.
For a binary verifier, $G_t$ may be the indicator that a certificate has appeared by time $t$; for a scalar verifier, it may be a predeclared normalization of verified improvement relative to the instance baseline.

For success threshold $\delta>0$, define
\[
\tau_\delta(a,x)=\inf\{t\in\{1,\ldots,H\}:G_t(a,x)\ge \delta\},
\]
with $\tau_\delta(a,x)=\infty$ if the threshold is never reached, and define certified occupancy
\[
\Occ_{\delta,H}(a,x)=\frac{1}{H}\sum_{t=1}^H \one\{G_t(a,x)\ge \delta\}.
\]
Let $C_{a,\tau_\delta\wedge H}(x)$ be the cost to first certification or horizon and $C_a^{H}(x)$ the cost accumulated through horizon.
Costs can be wall-clock time, verifier time, token/API cost, or a predeclared linear combination.
We use
\begin{align}
\ell_{\mathrm{hit}}(a,x)
&= \one\{\tau_\delta(a,x)=\infty\}+\lambda\,C_{a,\tau_\delta\wedge H}(x),
\\
\ell_{\mathrm{occ}}(a,x)
&= 1-\Occ_{\delta,H}(a,x)+\lambda\,C_a^{H}(x),
\\
\ell_{\log,\delta,\rho}(a,x)
&=
\log C_{a,\tau_\delta\wedge H}(x)
+
\rho\,\one\{\tau_\delta(a,x)=\infty\},
\label{eq:log-effort-loss}
\end{align}
where $\lambda$ converts cost into the same deployment scale and $\rho>0$ is a failure penalty.
These losses make explicit why final verifier score alone can rank workers differently from deployment value: first certification, persistence, latency, and token cost are all part of the decision criterion.

\section{Value of Diagnostic Information}
\label{sec:accounting}

The central theoretical object is the deployment loss achieved after buying a diagnostic measurement and selecting an action.
The following quantities compare static choice, diagnostic information, and the learned router that uses that information.

\subsection{Static context, diagnostic signal, and learned router}

The best fixed-action loss is
\begin{equation}
L_{\mathrm{fix}}
:=
\min_{a\in\cA} \E[\ell(a,X)].
\label{eq:lfix}
\end{equation}
This is the strongest policy available to a practitioner who must choose one action for the entire deployment distribution before seeing instance-specific context.

The static-context Bayes loss is
\begin{equation}
L_W
:=
\E\left[\min_{a\in\cA}\E[\ell(a,X)\mid W]\right].
\label{eq:lwork}
\end{equation}
This is the value of already-available context, before any additional verifier-backed measurement is purchased.

For diagnostic measurement $b\in\cB$, define the raw diagnostic Bayes loss
\begin{equation}
\bar L_b
:=
\E\left[\min_{a\in\cA}\E[\ell(a,X)\mid W,Z_b]\right]
\label{eq:rawlzb}
\end{equation}
and the net diagnostic Bayes loss
\begin{equation}
L_b
:=
\E[c_b(X)]+\bar L_b.
\label{eq:netlzb}
\end{equation}
The raw quantity isolates the decision value of the signal; the net quantity asks whether that value survives after paying for the measurement.

A learned router after diagnostic measurement $b$ is a measurable policy $r_b(a\mid W,Z_b)$ over the finite action menu, with deployment objective
\begin{equation}
\J_b(r_b)
:=
\E\left[c_b(X)+\sum_{a\in\cA} r_b(a\mid W,Z_b)\,\ell(a,X)\right].
\label{eq:routed-objective}
\end{equation}
When counterfactual outcomes for all actions are logged on the same held-out instance, we also report instance-level action regret
\[
\reg_\ell(R,b;X)
=
\ell(\hat a_R(W,Z_b),X)-\min_{a\in\cA}\ell(a,X),
\]
where $\hat a_R(W,Z_b)$ is the action selected by router $R$.

\subsection{Diagnostic value accounting}

\begin{definition}[Static opportunity, diagnostic value, and router gap]
For each admissible diagnostic measurement $b\in\cB$, define
\begin{align}
\Delta_W
&:= L_{\mathrm{fix}}-L_W,
\\
\bar\Delta_b
&:= L_W-\bar L_b,
\\
\Delta_b
&:= L_W-L_b = \bar\Delta_b-\E[c_b(X)],
\\
\Reg_b(r_b)
&:= \J_b(r_b)-L_b.
\end{align}
Here $\Delta_W$ is the value of static context, $\bar\Delta_b$ is the raw value of the diagnostic signal, $\Delta_b$ is its net value after measurement cost, and $\Reg_b(r_b)$ is the learned router's gap to the diagnostic Bayes decision.
\end{definition}

\begin{theorem}[Diagnostic value accounting identity]
\label{thm:main-identity}
For every admissible diagnostic measurement $b\in\cB$ and learned router $r_b$,
\begin{equation}
\J_b(r_b)
=
L_{\mathrm{fix}}-\Delta_W-\Delta_b+\Reg_b(r_b).
\label{eq:main-identity}
\end{equation}
Equivalently, $\J_b(r_b)=L_W-\Delta_b+\Reg_b(r_b)=L_b+\Reg_b(r_b)$.
\end{theorem}

\begin{proof}
By definition, $\Reg_b(r_b)=\J_b(r_b)-L_b$.
Substituting $L_b=L_W-\Delta_b$ gives $\J_b(r_b)=L_W-\Delta_b+\Reg_b(r_b)$.
Substituting $L_W=L_{\mathrm{fix}}-\Delta_W$ yields~\eqref{eq:main-identity}.
\end{proof}

The identity is not the router's deployment rule.
It is an accounting language for interpretation.
A deployment can improve on the best fixed action because static context matters, because verifier-derived diagnostics add net value beyond static context, or because the learned router loses less value relative to the diagnostic Bayes action.
This keeps the paper's empirical question concrete: does $Z_b$ change the actual router's action, and does that action reduce deployment loss after the measurement cost is charged?

\subsection{Minimum useful diagnostic interaction}

\begin{definition}[Minimum useful diagnostic interaction]
\label{def:minimal-useful}
Fix a recovery fraction $\eta\in(0,1]$.
The minimum sufficient diagnostic interaction is any solution of
\begin{equation}
 b^{\mathrm{suf}}_\eta
 \in
 \argmin_{b\in\cB}
 \left\{\E[c_b(X)] : \bar\Delta_b \ge \eta\,\max_{b'\in\cB}\bar\Delta_{b'}\right\}.
 \label{eq:min-sufficient}
\end{equation}
The economically optimal diagnostic interaction is any solution of
\begin{equation}
 b^{\mathrm{net}}_\star
 \in
 \argmax_{b\in\cB} \Delta_b.
 \label{eq:net-optimal}
\end{equation}
\end{definition}

The first quantity asks for the cheapest admissible measurement that recovers most of the available diagnostic value.
The second asks which measurement maximizes deployment value after cost.
They need not coincide: a richer diagnostic record can be more informative and still not worth buying.
If $Z_{b_1}$ is measurable with respect to $Z_{b_2}$, then $b_2$ cannot increase the raw Bayes loss $\bar L_b$, because conditioning on a finer signal can only enlarge the class of measurable decision rules.
After cost is charged, however, the richer measurement may be worse.

\subsection{Connection to Achille--Soatto}

The framework above is the finite-action version of the Achille--Soatto view of verifiable agents as time-limited transductive solvers.
The deployment loss $\ell$ operationalizes ``time to verified success'' under a fixed verifier, budget, and cost convention.
The diagnostic signal $Z_b$ is therefore not an intrinsic model score and not a latent task label.
It is useful only when it moves the selected action toward a shorter or cheaper verified path on the current instance.

\section{Reusable Evaluation Records}
\label{sec:selection}

The experiments avoid black-box racing every router-information condition from scratch.
Instead, the pilot logs reusable diagnostic records and counterfactual worker trajectories.
Given a candidate design $d=(b,r_b)$ with objective $\J(d):=\J_b(r_b)$, the selected design from $N$ pilot instances is denoted $\hat d_N$ and its selection regret is
\begin{equation}
\Reg_{\mathrm{sel}}(N)
:=
\E\big[\J(\hat d_N)-\min_{d\in\cD}\J(d)\big].
\label{eq:selection-regret}
\end{equation}
This is a supporting diagnostic for evaluation efficiency, not the main claim.

\begin{algorithm}[Reusable pilot protocol for diagnostic model choice]
\label{alg:pilot}
\normalfont\small
\begin{tabular}{@{}r p{0.86\linewidth}@{}}
\textit{Input:} & worker menu $\cM$, diagnostic ladder $\cB$, router family, verifier-indexed deployment loss $\ell_V$, pilot split, holdout split.\\[0.25em]
1 & For each pilot instance and admissible measurement $b$, execute the standardized diagnostic measurement against verifier $V$, log $Z_b$, and record cost $c_b$.\\
2 & Execute the complete worker menu from the original instance state and log no-stop deployment trajectories and losses.\\
3 & Query the same router under each information state, including $W$ only and $W+Z_b$, and score the selected worker by the predeclared deployment loss.\\
4 & Evaluate holdout instances by reporting allocation shifts, paired selected-worker deployment-loss changes, diagnostic cost, and supporting oracle or selection-regret diagnostics when useful.
\end{tabular}
\end{algorithm}

The expensive objects are the worker trajectories and diagnostic measurements, not the number of router prompts evaluated on top of them.
This amortization lets the empirical section compare router information states under a fixed deployment loss while keeping oracle and selection-regret analyses as supporting diagnostics.

\section{Experimental campaign}
\label{sec:experiments}

This section specifies the paper-facing campaign.
The main evidence is router-facing: hold the router model, worker menu, task instances, and deployment loss fixed; vary only the diagnostic information shown to the router; then measure whether the router changes its allocation and whether the selected workers achieve lower deployment loss.
Oracle quantities are useful sanity checks, but they are not the main experimental claim.

\subsection{Benchmark family and operational instantiation}
\label{subsec:benchmark}

The experimental family is AutoResearch-style CIFAR-10 optimization.
Each instance contains an editable starting program \texttt{train.py}, a fixed training and validation regime, an external verifier based on validation loss, and a replicate seed.
The verifier is the evaluation harness that runs the program and returns validation metrics; it is not contained in \texttt{train.py}.
The mainline task instances are indexed as
\[
X_{f,s}=(\texttt{train.py}_{f,0},D_f,V,B_V,s),
\]
where $f$ is the task family, $s$ is the replicate seed, $D_f$ is the data/regime specification, $V$ is the verifier, and $B_V$ is the fixed verifier training budget.
We use three compact network families: \emph{flat multilayer perceptron}, \emph{compact convolutional network}, and \emph{tiny residual network}.
They intentionally vary the starting model class while keeping the artifact interface and verifier fixed.
The seed $s$ controls data subset realization, shuffle, augmentation, label noise or imbalance when used, and model initialization whenever the implementation permits a unified seed.
For the main pilot we use five seeds per family, so the full worker matrix contains $3$ families $\times$ $5$ seeds $\times$ $3$ workers $=45$ no-stop full trajectories before router evaluations.
Additional repeated LLM trajectories on a smaller subset estimate stochasticity of the agent optimization path.

The paper-facing worker menu is the Claude-family depth menu
\[
\cM=\{\texttt{haiku},\ \texttt{sonnet},\ \texttt{opus}\}.
\]
The main router is an \texttt{opus} prompt-only orchestrator implemented in the evaluation harness.
It observes a diagnostic signal, returns a JSON decision over the worker menu, and does not edit \texttt{train.py} itself.
This keeps routing ability separate from hidden tool policy: the harness controls reset state, logging, worker prompts, and counterfactual worker trajectories.

We evaluate a nested family of router-visible diagnostic signals.
The fixed ladder is
\[
Z_0 \subset Z_{\mathrm{file}} \subset Z_{\mathrm{base},1} \subset Z_{\mathrm{base},2},
\]
where $Z_0$ is the empty no-diagnostic signal, so the router sees only $W$; $Z_{\mathrm{file}}$ adds the initial \texttt{train.py} and workload summary; and $Z_{\mathrm{base},r}$ adds $r\in\{1,2\}$ cheap verifier-only baseline probes of the unmodified program.
Each baseline probe records validation loss, validation accuracy, validation bits-per-byte when applicable, training seconds, total seconds, total optimizer steps, parse/runtime status, and the diagnostic seed or budget used for the probe.
After observing $Z_b$, the router selects the worker that carries out deployment from the original artifact state.

\subsection{Operational budgets, utilities, and logging}
\label{subsec:ops}

The worker horizon is fixed at $H=20$ edit steps, long enough to observe first hits and persistence while keeping the full counterfactual worker matrix feasible; the appendix reports the calibration behind this choice.
Each edit step consists of one worker reasoning/code-generation call, materialization of the proposed structured edit, and one verifier run on the resulting \texttt{train.py}.
The main campaign fixes a single verifier training budget $B_V$ for all verifier calls.
Varying $B_V$ would test verifier-budget sensitivity, but it is held fixed here so the experimental conditions differ in router-visible information rather than in the scoring rule itself.
Before the final campaign, we run a calibration sweep over
\[
B_V\in\{32,128,256,512\}
\]
and choose the smallest budget for which baseline measurements are stable, worker edit rankings are not dominated by verifier noise, and runtime remains feasible.
We also measure verifier runtime across the three network families before the final campaign to ensure that one architecture does not dominate the deployment loss purely through an uncontrolled evaluation-time effect.

The primary success thresholds are relative improvements
\[
\delta\in\{0.05,0.10,0.15,0.20\}.
\]
The $5\%$ threshold is the primary claim threshold; larger thresholds are reported as sensitivity because they can be too severe for short-budget AutoResearch instances.
Full trajectories always run to horizon $H$ even after the first threshold hit.
This lets us reconstruct first-hit cost while also measuring persistence and final performance.

The primary routing utility is a cost-aware persistence loss.
For worker $m$ on instance $X$, define
\[
\ell_{\mathrm{deploy}}(m,X)
=
\alpha\bigl(1-\Occ_{\delta,H}(m,X)\bigr)
+\beta\,\one\{\tau_\delta(m,X)=\infty\}
+\lambda_T \widetilde T_{m,H}(X)
+\lambda_K \widetilde K_{m,H}(X),
\]
where $\widetilde T$ and $\widetilde K$ are predeclared normalized wall-clock and token costs.
The primary report fixes $(\alpha,\beta,\lambda_T,\lambda_K)$ before evaluation and reports sensitivity to wall-clock-only, token-only, and censored log-effort variants.
For each router decision, the selected worker is scored by $\ell_{\mathrm{deploy}}$ from its deployment trajectory on the same instance; counterfactual worker trajectories are logged to avoid rerunning the worker matrix for every router-information condition.

Every router decision record stores task family, replicate seed, diagnostic condition, diagnostic verifier calls, diagnostic wall time, router model, router input and output tokens, router dollar cost, router wall time, selected worker, worker ranking, confidence, success-probability estimates, expected cost-to-success estimates, and diagnostic features used.
Every worker-step record stores step index, worker model, input and output tokens, reasoning wall time, API cost, verifier training steps, verifier training seconds, verifier wall time, validation loss, validation accuracy, relative improvement, success indicators for all thresholds, parse failures, runtime failures, and whether the artifact was promoted as the visible parent.
Every run summary stores baseline loss, best loss, final loss, first-hit step for each threshold, hit indicators, threshold occupancy, total reasoning time, total verifier time, total wall-clock time, total tokens, total cost, total verifier calls, and $\ell_{\mathrm{deploy}}$ under the frozen cost convention.
Uncertainty intervals are computed by nonparametric bootstrap resampling at the task-family level with seeds nested inside families; when worker-run stochasticity is explicitly replicated, the bootstrap resamples task instances first and agent-run replicates second.

The router output contract is fixed before evaluation.
For a worker-routing decision it must return exactly one selected worker in $\{\texttt{haiku},\texttt{sonnet},\texttt{opus}\}$, a complete worker ranking, per-worker success-probability estimates, per-worker expected cost-to-success estimates or null values when no success is expected, an expected final-loss ranking, a scalar confidence, a list of diagnostic features used, and a brief rationale grounded only in the allowed diagnostic record.
The router prompt explicitly states that the router must not optimize \texttt{train.py}, must not propose edits, and must prefer the cheapest worker likely to reach the relative-improvement success criterion.

\subsection{Experiment I: worker rankings under verifier and deployment losses}
\label{subsec:exp1}

The first experiment establishes the decision objective before any router is introduced.
For each family--seed instance $X_{f,s}$ and every worker $m\in\cM$, we run a full no-stop trajectory up to horizon $H$ from the same initial artifact state.
We then rank workers under verifier-facing criteria such as final validation loss or bits-per-byte, relative improvement, and hit rate, and compare those rankings with the deployment loss $\ell_{\mathrm{deploy}}$ from Section~\ref{subsec:ops}.
This experiment asks whether the worker that looks best under the scalar verifier metric is still best once persistence above threshold, no-hit penalty, wall-clock time, and token cost are charged.
The output is a rank-flip analysis over task families and replicate seeds, together with confidence intervals obtained by the bootstrap scheme described above.

\subsection{Experiment II: router allocation under diagnostic information}
\label{subsec:exp2}

The second experiment tests whether diagnostic information changes the routing decision itself.
For every instance, we query the same prompt-only router under the nested information ladder
\[
W,\quad W+Z_{\mathrm{file}},\quad W+Z_{\mathrm{base},1},\quad W+Z_{\mathrm{base},2}.
\]
The router returns a selected worker, a worker ranking, and calibrated estimates in the fixed JSON format.
No worker performance comparison is made in this experiment; the estimand is the allocation distribution induced by each information state.
We report worker-choice frequencies and pairwise choice-shift rates relative to the $W$-only condition.
If $Z_b$ does not change the allocation, then the diagnostic interaction is not decision-relevant for this router; if it does, the next experiment asks whether the change improves deployment loss.

\subsection{Experiment III: selected-worker deployment loss under routing}
\label{subsec:exp3}

The third experiment scores the consequences of the allocation changes measured in Experiment~II.
For each instance and information state, the router selects one worker, and that decision is scored by the selected worker's no-stop deployment trajectory on the original instance state.
The worker trajectories are the same counterfactual trajectories collected in Experiment~I; changing $Z_b$ changes only the router decision, not the worker's optimization dynamics.
Let $m_R^0(X)$ be the worker selected when the router sees only $W(X)$, and let $m_R^b(X)$ be the worker selected when it sees $W(X)$ together with the diagnostic record $Z_b(X)$.
The paired estimand is
\[
\Delta_{\mathrm{router}}(b)
=
\E\!\left[
\ell_{\mathrm{deploy}}(m_R^0(X),X)
-
\ell_{\mathrm{deploy}}(m_R^b(X),X)
-
c_b(X)
\right],
\]
Positive $\Delta_{\mathrm{router}}(b)$ means the diagnostic record changed routing in a way that improved net deployment loss.
We report paired bootstrap intervals, mean selected-worker deployment loss by information state, the diagnostic cost term $c_b$, and the subset of instances where the router changed worker but increased loss.

\subsection{Experiment IV: minimum useful diagnostic interaction}
\label{subsec:exp4}

The fourth experiment turns the diagnostic ladder into a cost-value curve.
Using the same paired scoring rule as Experiment~III, we compute $\Delta_{\mathrm{router}}(b)$ for every fixed information state in the ladder.
The reported quantities are the choice-shift rate, the gross selected-worker deployment-loss reduction, diagnostic cost, and net $\Delta_{\mathrm{router}}(b)$.
The minimum useful diagnostic interaction is the cheapest admissible $b$ with positive net paired gain, or the router-facing analogue of Definition~\ref{def:minimal-useful}: the cheapest $b$ that recovers a predeclared fraction of the best observed paired gain.

\section{Discussion}
\label{sec:discussion}

The three-family mainline is intentionally small.
It trades breadth for paired, controlled routing comparisons: for each family--seed instance, the same router is queried under $W$ only and under $W+Z_b$, and the selected workers are scored under the same deployment loss.
The main interpretive risk is that a router could exploit static family identity rather than live verifier feedback.
We address this by making the $W$-only condition the baseline, then reporting allocation shifts and paired deployment-loss changes under the same task instances and worker trajectories.
If a cheap diagnostic measurement changes allocation and lowers net deployment loss, then the signal is operationally useful.
If it changes allocation but not loss, the router is sensitive to the signal but uses it poorly; if it does not change allocation, the admitted diagnostic family is not decision-relevant for that router.

\paragraph{Beyond AutoResearch.}
AutoResearch is the controlled empirical substrate, not the scope of the formalism.
The same formal objects apply to other verifier-backed tasks by changing the verifier and the admissible probe family: in repository repair, $V$ is the test suite and $b$ may be a smoke-test or failing-test probe; in theorem proving, $V$ is a proof checker and $b$ may be a bounded search or tactic replay; in data-pipeline construction, $V$ is schema, unit, or validation-data compliance and $b$ may be a dry run on a small shard.
The empirical claim of this paper is established on AutoResearch because it is cheap enough to instrument densely; the broader claim is methodological: once a verifier can produce a cheap diagnostic signal, the same accounting estimates whether routing on that signal is worth paying for.

The main limitation is that all value estimates are conditional on the verifier, budget, and diagnostic family.
A probe can be too weak to expose useful structure, or too expensive to be worth running even when it is informative.
The analysis also assumes that pilot and holdout instances are drawn from the same deployment distribution; robustness workloads should therefore be reported as distribution-shift stress tests rather than as the primary evidence for the main claim.

\paragraph{Future experimental extensions.}
The main campaign can be extended with shuffled or mismatched diagnostic records as negative controls, repeated router queries to separate diagnostic effects from router stochasticity, sensitivity sweeps over $(\alpha,\beta,\lambda_T,\lambda_K)$, diagnostic-cost breakeven curves, family-held-out generalization tests, and router-model ablations that compare stronger and cheaper orchestrators under the same worker menu.

\section{Conclusion}
\label{sec:conclusion}

Minimal diagnostic interaction reframes model choice for verifier-backed agents as a measurable deployment decision.
Given a verifier, a budget, and a finite menu of worker models or harness actions, the paper asks how much cheap interaction is enough to select the action for the current instance.
The answer is not a universal model ranking, but a paired evaluation of whether verifier-derived information changes router allocation and lowers selected-worker deployment loss after measurement cost is paid.
This makes AutoResearch a controlled testbed for a broader claim: in verifiable transductive tasks, useful routing information is the information that improves cost-aware verified performance on the current instance.
